# M9.0 — Reproducible Product Baseline

Status: DESIGN APPROVED / IMPLEMENTATION NOT STARTED

Product baseline commit: `2491d7d5e4e90d380b45c4baee3f2d023008b1a4`

Program mode:

- `M9 = PRODUCT HARDENING + DEMO READINESS`
- previous refresh/provenance work is deferred
- PMTiles/offline-area expansion is deferred
- routing/GPX is deferred
- `LEGAL=FROZEN`
- `M7=PAUSED`

M9.0 is diagnostic. It may add QA tooling, scripts, configuration, documentation and evidence. It MUST NOT modify product behavior.

## 1. Objective

Create a reproducible baseline of the current AlRaso product before any M9 hardening work begins.

The baseline must answer, with machine-readable evidence:

1. What does the application look like in its current state?
2. Which critical product flows work in a real Chromium browser?
3. Which defects are present, where, and with what severity?
4. What are the current architecture and quality characteristics?
5. Can the same evidence be regenerated twice without changing product code?

M9.0 does not improve the application. It measures it.

## 2. Frozen product boundary

The following files and behavior are frozen for M9.0:

- `webapp/static/app.js`
- `webapp/static/style.css`
- `webapp/static/index.html`
- `webapp/server.py`
- resolver implementation
- corpus
- legal rules
- legal publication/review state

Allowed M9.0 changes are limited to:

- QA tooling
- Playwright configuration
- Node package metadata and lockfile for the QA harness
- scripts used to execute or summarize the baseline
- CI workflow/configuration required to run the harness
- documentation
- generated baseline evidence
- machine-readable findings

No feature, product fix, copy fix, CSS fix, backend fix or legal fix may be made during M9.0.

If a defect is found, it is recorded as evidence and classified. It is not fixed inside the baseline milestone.

## 3. QA harness architecture

The browser harness will be isolated from the Python product runtime.

Recommended structure:

```text
qa/browser/
├── package.json
├── package-lock.json
├── playwright.config.*
├── tests/
│   └── baseline.spec.*
├── helpers/
└── scripts/
```

Rules:

- Node is QA tooling only.
- Playwright is QA tooling only.
- `@playwright/test` version is pinned.
- Chromium version is pinned through the Playwright package/browser install used by the harness.
- The product remains build-step-free.
- The core Python package remains independent of Node.
- The harness launches the real application with `python webapp/server.py --host 127.0.0.1 --port 8765`.
- The harness uses real Chromium.
- The harness must not replace product responses with invented JSON.
- Fault injection may abort real transport but may not mock successful product responses.

## 6. Canonical scenario catalogue

M9.0 contains exactly 14 initial canonical scenarios. Scope changes require an explicit design change.

### S01_BOOT_EMPTY

Purpose: initial application load.

Assertions include:

- application loads
- map is present
- no point is selected
- primary UI is usable
- no unexpected page error
- no unexpected console error

### S02_SEARCH_KNOWN_PLACE

Purpose: known-place search and selection.

Assertions include:

- canonical query resolves through the real app
- selected place is displayed
- legal answer section becomes visible

### S03_COORDS_UNKNOWN

Purpose: verify current UNKNOWN/UNDETERMINED product presentation.

Canonical input should use an existing outside-coverage point from the product data, preferably the current `coverage.json` example point.

Assertions include:

- `UNDETERMINED`
- unknown/no normative coverage presentation
- compact user-facing answer visible
- technical detail remains available

### S04_PICOS_PERMITTED

Purpose: exercise a canonical positive legal determination.

Rules:

- use the existing canonical Cantabria point `43.17068, -4.80299`
- required factual inputs are entered through the UI
- do not require local DEM
- do not install Rasterio solely for this scenario
- no hidden fact injection by the harness

Expected result: `PERMITTED` under the canonical facts already covered by existing tests.

### S05_POI_NAMED

Purpose: named POI interaction.

Assertions include:

- named POI can be selected
- real name is visible
- provenance is accessible
- legal CTA is available

### S06_POI_UNNAMED

Purpose: unnamed POI fallback behavior.

Assertions include:

- technical source references are not used as map labels
- card uses the category-based unnamed presentation
- source reference appears only in provenance/detail

### S07_PROTECTED_AREA

Purpose: M8.1 protected-area context.

Assertions include:

- protected-area polygon can be selected
- protected-area context is visible
- non-legal disclaimer is visible
- legal CTA uses clicked coordinates only

### S08_WEATHER_AVAILABLE

Purpose: real Open-Meteo success path.

Rules:

- real network request
- no mocked successful weather response
- observed weather values are volatile evidence
- temperature or forecast-value drift alone must not fail the scenario

Record:

- observation timestamp
- requested URL or normalized request metadata
- HTTP status
- stable UI structure/visibility assertions

### S09_WEATHER_UNAVAILABLE

Purpose: weather transport failure.

Method:

- abort the real Open-Meteo network request in Chromium
- do not return invented weather data

Expected fault:

```text
weather_unavailable
```

The injected failure is expected and must not be counted as an unexpected harness failure.

Assertions include:

- honest unavailable state
- legal resolution remains usable
- stale weather is not presented as current

### S10_SAVE_FAVORITE

Purpose: local favorite flow.

Assertions include:

- point can be saved
- Guardados reflects the new item
- state persists within the scenario context as intended

### S11_OUTING_FLOW

Purpose: outing creation and reuse.

Assertions include:

- create outing
- add a place
- reopen chooser
- existing outing remains selectable

### S12_MOBILE_SHEET

Purpose: mobile bottom-sheet interaction.

Assertions include:

- closed/peek/full interaction works
- primary content remains reachable
- no critical horizontal overflow
- map remains usable

Desktop execution still records the scenario result, but mobile-specific assertions apply only where the mobile layout is active.

### S13_OFFLINE_VISITED

Purpose: PWA behavior after prior visit.

The scenario has two explicit phases:

1. online preparation
2. offline execution

Rules:

- each scenario begins isolated
- S13 performs its own online preparation before going offline
- no pre-existing service-worker/cache state may leak from another scenario

Assertions include:

- visited shell/resources remain available according to current M5 behavior
- API behavior remains fail-closed/network-only
- stale weather is not presented as a fresh observation

### S14_LEGAL_SERVER_DOWN

Purpose: stale legal-result protection.

Sequence:

1. resolve one valid legal case successfully using the real backend
2. initiate a second legal resolution
3. abort the second real `/api/resolve` transport request

Rules:

- first response is real
- second response is not mocked
- transport is aborted only for the second legal request

Expected fault:

```text
resolve_request_aborted
```

Critical assertion: the previous valid legal result must not be represented as a newly computed result for the second request.

## 7. Scenario isolation and canonical inputs

Every scenario defines explicitly:

- canonical coordinates or search input
- activity
- factual inputs
- date/preconditions where required
- expected initial storage state
- expected fault injection, if any
- expected stable assertions

Each scenario starts with an isolated browser context.

No localStorage, service worker, cache storage or cookies may leak between scenarios unless created by the scenario itself.

S13 is the deliberate exception only in the sense that its online and offline phases occur in the same scenario context.

## 8. Viewport matrix

Every canonical scenario is executed at:

- `1440x900`
- `390x844`
- `360x800`

Total required combinations:

```text
14 scenarios × 3 viewports = 42 combinations
```

A viewport-specific behavior may have conditional assertions, but every combination must produce a structured result.

## 9. Scenario result contract

Each execution result must separate execution status from product findings.

Minimum structure:

```json
{
  "scenario": "S09_WEATHER_UNAVAILABLE",
  "viewport": "390x844",
  "scenario_status": "PASS",
  "reproducible": true,
  "assertions": {
    "passed": 0,
    "failed": 0
  },
  "unexpected_console_errors": 0,
  "console_warnings": 0,
  "page_errors": 0,
  "expected_faults": ["weather_unavailable"],
  "unexpected_network_failures": [],
  "findings": []
}
```

`PASS` means the scenario was reproducible and its stable assertions passed.

`PASS` does not mean the UX is good.

A visually poor but reproducible result may be `PASS` with one or more findings.

Harness/runtime failures use separate statuses such as:

- `HARNESS_ERROR`
- `ENVIRONMENT_ERROR`
- `NON_REPRODUCIBLE`

These are not P0-P3 product severities.

## 10. Metrics captured

M9.0 records baseline measurements; it does not invent performance budgets.

At minimum record where available:

- scenario duration
- navigation/boot duration
- `/api/config` timing
- `/api/places` timing
- `/api/pois` timing
- `/api/protected-areas` timing
- `/api/coverage` timing
- `/api/find` timing
- `/api/resolve` timing
- request count
- transferred bytes when available from Chromium
- failed requests
- expected failed requests
- unexpected console errors
- console warnings
- page errors
- unhandled exceptions/rejections where observable
- critical horizontal overflow
- critical elements outside viewport

M9.0 does not fail a scenario because a metric is slow unless the scenario itself cannot complete reliably. Performance thresholds belong to later M9 work after the current baseline is known.

## 11. Volatile data policy

Dynamic external data must be distinguished from stable product structure.

Initial volatile fields:

```json
[
  "weather.temperature",
  "weather.observed_at"
]
```

Weather observations must be stored as evidence, but a changed temperature or forecast value must not by itself cause baseline failure.

Visual screenshot SHA-256 values are integrity hashes, not visual-equivalence assertions.

The system MUST NOT require:

```text
sha256(run1.png) == sha256(run2.png)
```

for a run to be reproducible.

## 12. Two-run reproducibility rule

M9.0 requires two consecutive baseline executions against the same product commit and harness commit.

Reproducibility requires:

- same canonical scenario inputs
- same 42 scenario/viewport combinations
- same stable assertion outcomes
- same `scenario_status` classification except volatile external observations
- same expected fault classification
- no unexpected harness/environment error
- no product-file drift

Volatile weather values and timestamps may differ.

## 14. Severity model

### P0 — critical

A defect that can materially violate product trust or critical integrity, including examples such as:

- unsafe legal conclusion
- stale legal determination presented as newly computed
- cartographic/POI data influencing legal determination
- critical security defect
- serious data corruption/loss
- legal-boundary violation

### P1 — demo/beta blocker

A defect that blocks a core user flow or makes the product materially misleading/unusable, including examples such as:

- core flow crash
- map unavailable with no usable recovery
- mobile sheet blocks critical interaction
- key control inaccessible by keyboard
- severe responsive breakage
- core action cannot complete

### P2 — material quality debt

A real UX, accessibility, performance, architecture or maintainability defect with a workaround and no immediate critical trust impact.

### P3 — polish/backlog

Minor visual consistency, spacing, wording, opportunistic refactoring or nonessential improvement.

Harness, CI or environment problems are never assigned P0-P3; they use harness/environment statuses.

## 18. M9.0 completion gate

M9.0 is complete only when all conditions below hold:

```text
M9.0 BASELINE COMPLETE

42/42 scenario×viewport combinations executed
2 consecutive reproducible executions completed
canonical evidence committed
manifest complete
all committed evidence hashes verified
findings classified
no finding lacks evidence
no harness error remains unresolved
no environment error remains unresolved
no NON_REPRODUCIBLE scenario remains unresolved
product_commit remains 2491d7d5e4e90d380b45c4baee3f2d023008b1a4
frozen product files unchanged
resolver/corpus/rules unchanged
```

P1, P2 and P3 findings do not block M9.0 closure.

A P0 does not invalidate evidence already collected and does not prevent M9.0 from being marked baseline-complete.

## 19. M9 continuation gate

After M9.0 baseline completion:

```text
M9 PROGRAM CONTINUE
→ baseline complete
→ no P0 in SECURITY, LEGAL_BOUNDARY, legal-result integrity or data integrity
```

```text
M9 PROGRAM BLOCKED
→ baseline complete
→ one or more critical P0 findings exist
```

If blocked, P0 remediation occurs in a separate explicit path. The baseline is not retroactively converted into implementation work.

## 22. Governing principle

M9.0 exists to prevent further development from being driven by anecdotal screenshots or ad-hoc fixes.

The milestone is successful when the current product state is objectively reproducible, inspectable and prioritized — even if that evidence shows that the current application is not yet demo-ready.
