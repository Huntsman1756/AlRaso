# M9.0 — Reproducible Product Baseline

Status: DESIGN REVISED / AWAITING FINAL APPROVAL

Product baseline commit: `2491d7d5e4e90d380b45c4baee3f2d023008b1a4`

Program mode:

- `M9 = PRODUCT HARDENING + DEMO READINESS`
- refresh/provenance is deferred
- PMTiles/offline-area expansion is deferred
- routing/GPX is deferred
- `LEGAL=FROZEN`
- `M7=PAUSED`

M9.0 is diagnostic. It may add QA tooling, scripts, CI configuration, documentation and evidence. It MUST NOT modify product behavior.

## 1. Objective

Create a reproducible baseline of the current AlRaso product before any M9 hardening work begins.

The baseline must answer, with machine-readable evidence:

1. What does the application look like at the frozen product commit?
2. Which critical product flows work in a real Chromium browser?
3. Which defects are present, where, and with what severity?
4. What are the current architecture and quality characteristics?
5. Can the same evidence be regenerated twice without changing product code?

M9.0 does not improve the application. It measures it.

## 3. QA harness architecture

The browser harness is isolated from the Python product runtime.

Target structure:

```text

├── package.json
├── package-lock.json
├── playwright.config.*
├── tests/
│   └── baseline.spec.*
├── helpers/
└── scripts/
```

Rules:

- Node is QA tooling only.
- Playwright is QA tooling only.
- `@playwright/test` is pinned to an exact version.
- Chromium is the Playwright-managed Chromium matching that pinned Playwright release.
- The product remains build-step-free.
- The core Python package remains independent of Node.
- The harness launches the real application with `python webapp/server.py --host 127.0.0.1 --port 8765`.
- The harness uses real Chromium.
- The harness MUST NOT replace product responses with invented JSON.
- Fault injection may abort real transport but may not fabricate successful responses.
- The canonical CI job does not install `alraso[dem]` or Rasterio.

### S08_WEATHER_AVAILABLE

S08 is a `LIVE EXTERNAL INTEGRATION PROBE`. Its execution is required, but
Open-Meteo availability is not a reproducibility blocker. S08 measures the
boundary between AlRaso and the real provider; S09 remains the controlled,
reproducible unavailable-provider path.

```text
S08_EXECUTION_REQUIRED = YES
S08_PROVIDER_AVAILABILITY_BLOCKS_REPRODUCIBILITY = NO
S09_UNAVAILABLE_PATH_BLOCKS = YES
```

Canonical input:

```text
query: Garganta de la Cares
expected place id: cares-picos
coordinates: 43.17068, -4.80299
network: real Open-Meteo request allowed
weather response timeout: 30 seconds
```

Rules:

- the browser starts the real Open-Meteo request; mocks, replay and fulfilled
  invented responses are forbidden
- the request event is observed independently from the response event
- the timeout is fixed at 30 seconds and MUST NOT be increased to accommodate
  provider variability
- the request URL MUST contain the canonical coordinates, using the precision
  produced by the product request serializer
- the legal result remains available and weather never becomes legal evidence

The provider observation is classified as:

```text
LIVE_OK
EXTERNAL_TIMEOUT
EXTERNAL_NETWORK_ERROR
EXTERNAL_HTTP_ERROR
```

`LIVE_OK` means that a real HTTP 200 response was observed. It activates the
positive integration assertions: valid weather UI structure and visible
Open-Meteo attribution. A 200 response with invalid UI is a product failure.

After an observed request, `EXTERNAL_TIMEOUT`, `EXTERNAL_NETWORK_ERROR` and
`EXTERNAL_HTTP_ERROR` are external observations. They do not fail S08 by
themselves. The request, its URL, the legal result and the stable product
assertions remain required. A missing request is different: it is a failed
S08 product/harness assertion, because AlRaso did not attempt the integration.

The external status MUST be recorded in raw evidence. For example:

```json
{
  "external_observation": {
    "provider": "open-meteo",
    "request_observed": true,
    "request_url": "https://api.open-meteo.com/v1/forecast?...",
    "response_observed": false,
    "status": "EXTERNAL_TIMEOUT",
    "response_http_status": null,
    "external_latency_ms": null,
    "ui_structure_valid": false,
    "attribution_visible": false
  }
}
```

Record:

- request-observed flag and request URL, even when no response arrives
- response-observed flag and HTTP status when available
- external status and provider latency when available
- observed weather timestamp and values when a response body is readable
- UI structure and attribution observations
- stable legal-availability and integration assertions

## 14. Two-run reproducibility rule

M9.0 requires two consecutive baseline executions against the same:

- `product_commit`
- `qa_harness_commit`
- `baseline_now`
- canonical scenario definitions
- viewport matrix

Reproducibility requires:

- same 42 scenario/viewport combinations
- same stable assertion outcomes
- same `scenario_status` classifications except fields explicitly declared volatile
- same expected-fault classifications
- no unresolved harness/environment error
- no product-file drift

Volatile weather observations and generation timestamps may differ. For S08,
the provider outcome may also differ: `LIVE_OK` in one run and
`EXTERNAL_TIMEOUT`, `EXTERNAL_NETWORK_ERROR` or `EXTERNAL_HTTP_ERROR` in the
other is reproducible when the request was observed with canonical
coordinates, no execution error occurred, legal state is stable and the
stable assertions match. A missing request, or a real 200 response whose UI
or attribution assertions fail, remains a product failure and is not made
acceptable by this rule.

No finding may exist without evidence and a reproduction path.

M9.0 records findings; it does not require detailed implementation solutions.

## 16. Severity model

### P0 — critical

A defect that can materially violate product trust or critical integrity, including:

- unsafe legal conclusion
- stale legal determination presented as newly computed
- cartographic/POI data influencing legal determination
- critical security defect
- serious data corruption/loss
- legal-boundary violation

### P1 — demo/beta blocker

A defect that blocks a core user flow or makes the product materially misleading/unusable, including:

- core flow crash
- map unavailable with no usable recovery
- mobile sheet blocks critical interaction
- key control inaccessible by keyboard
- severe responsive breakage
- core action cannot complete

### P2 — material quality debt

A real UX, accessibility, performance, architecture or maintainability defect with a workaround and no immediate critical trust impact.

### P3 — polish/backlog

Minor visual consistency, spacing, wording, opportunistic refactoring or nonessential improvement.

Harness, CI and environment problems are never assigned P0-P3; they use harness/environment statuses.

```text
M9 PROGRAM BLOCKED
→ M9.0 BASELINE COMPLETE
→ blocking_p0_count > 0
```

If blocked, remediation occurs in a separate explicit path. The baseline is not retroactively converted into implementation work.

## 22. Downstream M9 structure

Subject to the continuation gate:

```text
M9.1  product + visual system hardening
M9.2  frontend architecture hardening
M9.3  backend + runtime hardening
M9.4  QA + accessibility + performance hardening
M9.5  demo readiness / release candidate
```

M9.1+ consumes M9.0 evidence directly. Another broad audit is not required before implementation begins.

## 23. Non-goals

M9.0 explicitly does not include:

- UI redesign
- icon replacement
- copy rewriting
- frontend modularization
- backend modularization
- resolver changes
- corpus changes
- legal-rule changes
- legal review
- new park coverage
- routing
- GPX
- PMTiles expansion
- data-refresh automation
- performance tuning
- accessibility remediation
- security remediation
- visual-difference auto-acceptance

Those activities may only begin after the baseline gate and M9 continuation decision.

## 24. Governing principle

M9.0 exists to prevent further development from being driven by anecdotal screenshots or ad-hoc fixes.

The milestone is successful when the current product state is objectively reproducible, inspectable and prioritized — even if that evidence shows the current application is not yet demo-ready.
