# AlRaso M10.2 — National Source Coverage + Refresh (diseño)

**Estado:** PENDIENTE DE APROBACIÓN del owner.
**Fecha:** 2026-09-16
**Base de diseño:** `origin/main` = `97a60ee209ba4865f18d5d22c2731875b15092cc`
(merge PR #40 — EvidencePacket v2.1 consumer, evidence-only).
**Rama de trabajo:** `docs/m10.2-national-source-refresh` (worktree
`.worktrees/m10.2-design`).
**Clasificación:** ARQUITECTÓNICO + INFRAESTRUCTURA DE FUENTES. No es una feature
de producto, no publica reglas legales nuevas y no toca el resolver.

Esta spec fija la arquitectura de M10.2 antes de escribir una sola línea. M10.2
es la fase que convierte la pipeline de evidencia de M10.1 (5 pilotos
reproducibles) en infraestructura nacional mantenible: **atlas completo de
fuentes, refresh determinista y señales de versión**. M10.2 **no** publica
conclusiones jurídicas nuevas: la publicación de respuestas legales queda para
M10.3+ y siempre pasa por revisión humana.

## 0. Decisión resumida

Enfoque **C — híbrido** (aprobado por owner):

```text
M10.2-A  NATIONAL SOURCE ATLAS    caracterización completa, cero ingesta
M10.2-B  REFRESH CORE             primitiva genérica de snapshot/diff
M10.2-C  VERSION SIGNALS          candidatos mecánicos BOE/DOGC, nunca publicación
```

La separación se justifica así: **A** elimina la incertidumbre sobre las fuentes
(las gacetas no sondeadas no se pueden agrupar por familia sin caracterizarlas);
**B** implementa una primitiva genérica independiente del derecho material;
**C** consume esa infraestructura para señales de versión. La alternativa
"A — jurisdiction-first" queda descartada por evidencia (§A.2): el eje de
variación real es el mecanismo de la fuente, no la jurisdicción — Picos exige
tres canales de gaceta distintos para un solo parque.

### A.2 Evidencia que fija el diseño

1. **La heterogeneidad es de mecanismo, no de jurisdicción** (G0 §6, matriz
   M10.1): los 5 pilotos comparten código; toda diferencia vive en
   `profile`/`fixture`. No hay ningún `if jurisdiction` en `pipeline/`.
2. **El atlas G0 es parcial**: caracterizadas 9 superficies de gaceta (BOE +
   ES-AR/AN/AS/CB/CL/CN/MD/CT). Sin caracterizar: BOIB, DOCM, DOE, DOG, BOR,
   BORM, BON, BOPV, DOGV + boletines de Ceuta y Melilla.
3. **Refresh no existe**: `change_detection.method` está en el schema pero no
   hay snapshot store, comparador ni estado "último conocido". Es el gap
   estructural real de M10.2.
4. **`consolidated_api` es stub**: BOE `from/to` sobre `fecha_actualizacion` +
   `texto/indice` por bloque y DOGC `vigència` + `idVersion` AKN están
   *verificados en G0* (fuerza: fuerte) pero no implementados.
5. **No existe parser `boe_xml`** (consolidado por bloques) — pendiente desde
   la spec M10 §C.3.
6. **Geo-bloqueo probado** (P3 + `observatorio-alegaciones` en producción): un
   timeout extranjero no significa fuente ausente; el executor de refresh debe
   poder vivir en red española.

## C. Arquitectura por sub-milestone

### C.1 M10.2-A — NATIONAL SOURCE ATLAS

**Objetivo:** cada dominio jurisdiccional relevante para cobertura futura de
espacios protegidos tiene una ruta de fuente oficial caracterizada:

```text
por dominio / superficie:
  discovery        (mecanismo → doc IDs estables)
  fetch            (doc ID → bytes + formato + marcador)
  format/parser    (familia de formato existente o nueva)
  identifiers      (IDs nativos estables por tipo de documento)
  reachability     (expectativa por runner_network + fallback)
  change detection (mecanismo + fuerza + cadencia realista)
  version signal   (consolidado/vigència | ninguno verificado)
  fallback         (canal alternativo registrado)
```

**Ejecución:** probes reproducibles con la maquinaria ya existente —
`tooling/m10_probe_verify.py` generalizado por perfil — preservando por probe:
URL oficial, timestamp de retrieval, `runner_network`, HTTP outcome, content
marker, `raw_sha256`, IDs estables, licencia/términos de reutilización,
mecanismo de change-detection. Sin OCR salvo estructura que lo haga inevitable
y justificado explícitamente.

**Salidas (evidencia, no producto):**

```text
discovery/evidence/m10.2-atlas/            probes por dominio
pipeline/sources/atlas/*.profile.json      perfiles candidatos (pueden quedar
                                           UNPROBED con razón explícita)
source-atlas.json                          matriz completa
family clustering                          dominio → familia de mecanismo
reachability/fallback matrix               por dominio × runner_network
change-detection matrix                    mecanismo, fuerza, cadencia
```

**Hipótesis de clustering a verificar** (semilla G0 + OSS, no conclusión):

| Familia | Mecanismo | Cubierta ya por | Probables miembros nuevos |
|---|---|---|---|
| Open-data API | dataset query → doc IDs | `bocyl_opendatasoft`, `dogc_socrata` | Euskadi (JSON), DOG (RDF), Aragón CKAN |
| TOC/sumario → doc | tabla POST/GET → ID | `boc_toc_post` | DOGV, BON, BOIB? |
| URL estable por ID | `doc_url_template` + `get_simple` | `boc_canarias_doc` | BOPA, BOCM, BORM, DOCM, DOE, BOR |
| CGI legado | query string → text | `boa_cgi` | (probablemente único) |
| Consolidado por bloques | API de normas | — (stub) | BOE, DOGC ELI/AKN |

Si -A confirma esta hipótesis, el coste marginal de las ~11 superficies restantes
es **0–3 providers discovery nuevos** y **0–2 parsers nuevos** (RDF/DOG,
`boe_xml`). Lo que -A descubra manda sobre esta tabla.

**No ingesta de producción, no parseo a reglas, no PRs de normas.**

### C.2 M10.2-B — REFRESH CORE

**Objetivo:** detectar cambios de fuente/evidencia y producir deterministamente
un nuevo ReviewPacket/diff — o nada.

```text
snapshot store versionado (evidence versionada, no producto)
  SnapshotRecord:
    {source_id, surface_id, doc_id,
     raw_sha256, canonical_sha256,
     canonicalizer_id, canonicalizer_version,
     etag?, last_modified?,
     fetch_outcome, reachability_observed,
     observed_at, runner_network}
        |
        v  refresh run (por perfil, change_detection.cadence)
  clasificador determinista:
        |
  SAME                  -> log; nunca ReviewPacket
  CHANGED_TRANSPORT_ONLY-> log (etag/fecha/bytes movieron; canonical igual)
  CHANGED_CONTENT       -> ReviewPacket via review.prepare_pr() existente
  UNREACHABLE           -> estado observacional registrado
                           (NUNCA borrado, NUNCA "ausente");
                           N consecutivos del perfil -> DISAPPEARED_SUSPECTED
                           -> ReviewPacket de alerta
  INVALID               -> content-marker/soft-404 falla de forma persistente
                           -> ReviewPacket de alerta (fuente degradada)
  REBASELINE_REQUIRED   -> canonicalizer cambió; re-baseline manual,
                           nunca clasificado como cambio de fuente
```

**Reglas:**

- El canonicalizer es stdlib, conservador y por familia: elimina solo ruido
  demostrado empíricamente (timestamps de fetch, tokens volátiles, contadores).
  `canonicalizer_id` + `canonicalizer_version` viajan en toda evidencia de
  comparación.
- Anti-falsos-positivos = doble hash + canonicalizer versionado (patrón OTA,
  endurecido: cambiar la herramienta no puede simular ni ocultar cambios).
- `UNREACHABLE` escribe un estado observacional con `observed_at` +
  `runner_network` + `fetch_outcome`; la evidencia anterior se conserva
  íntegra. La desaparición es una *sospecha revisable*, no un borrado.
- La apertura de PR sigue controlada por humano (patrón foul-flock: refresh
  automático → ReviewPacket → PR humano). Automatizar la apertura requiere
  aprobación separada.
- Bitemporalidad intacta: refresh solo escribe `recorded_at`/`recorded_until`
  en evidencia nueva; jamás muta `effective_*` ni reglas publicadas. Un fetch
  que contradice una regla publicada abre ReviewPacket con diff — nunca
  sobrescribe.
- Executor: deployment inicial `es_local` (scheduled runner); la arquitectura
  es agnóstica — `runner_network` se registra en cada observación y ningún
  provider asume red. `foreign_ci` es observador válido / ejecutor degradado.

### C.3 M10.2-C — VERSION SIGNALS

**Objetivo:** donde la fuente expone consolidación/vigencia mecánica,
producir `VersionClaim` candidatos reales en vez del stub.

```text
BOE    : list ?from&to sobre fecha_actualizacion (corpus)
         + texto/indice por bloque (change detection granular)
         -> parser boe_xml por bloques (familia nueva, una)
DOGC   : Socrata vigència + ELI + idVersion AKN
         (canal ya verificado en G0/P4)
```

**Contrato:**

- `RESOLVED` solo donde la resolución sea **mecánicamente demostrada** con la
  evidencia conservada en `resolver_evidence` (endpoint + respuesta + fecha).
- Todo lo demás sigue `REQUIRES_MANUAL_REVIEW` — es el default, no el fracaso.
- `effective_from` conservador (regla ya congelada en M10.1 §7.4): solo
  evidencia estructurada o fecha exacta prerregistrada; `vacatio` en texto
  libre → `null` + `REQUIRES_MANUAL_REVIEW`. Cero interpretación de vacatio.
- Candidato ≠ publicable: `RESOLVED` significa "versión documental resuelta
  mecánicamente"; no crea `legal_rule_version`, no toca `official_status`,
  no promueve scope.
- Consolidated/version APIs producen **VERSION CANDIDATES**: señales de
  evidencia, no verdad legal. `VERIFIED_SOURCE != TRUE_INTERPRETATION`.

## D. Respuestas a las preguntas del mandato

- **Qué es M10.2 / qué se difiere:** infraestructura de fuentes (atlas,
  refresh, señales de versión). Se difiere a M10.3+: publicación de nuevas
  respuestas legales, ingesta de producción al corpus, automatización de
  apertura de PRs.
- **Jurisdicciones cubiertas:** 20 dominios administrativos (17 CCAA + Ceuta
  + Melilla + Estado); número de fuentes = evidence-driven.
- **Providers M10.1 reutilizables sin cambio:** los 5 de discovery, las 3
  recipes de fetch, `discovery_request()`, el verificador, el ReviewGate —
  todos. Nuevos solo donde -A demuestre un mecanismo no cubierto.
- **Change detection:** `SnapshotRecord` + clasificador de seis estados sobre
  `CanonicalEvidence` versionada.
- **SAME/CHANGED/UNREACHABLE/INVALID:** §C.2 (más `REBASELINE_REQUIRED`).
- **ReviewPacket cuándo:** solo `CHANGED_CONTENT`, `DISAPPEARED_SUSPECTED` e
  `INVALID` persistente. `SAME`/`TRANSPORT_ONLY`/`UNREACHABLE` < N: log, sin
  ruido.
- **Falsos positivos:** doble hash + canonicalizer conservador versionado;
  cambio de normalizador = `REBASELINE_REQUIRED`, jamás cambio de fuente.
- **Bitemporal:** refresh escribe solo `recorded_*` en evidencia nueva;
  reglas intocadas.
- **Desaparición/supersession:** estados observacionales (`UNREACHABLE`,
  `DISAPPEARED_SUSPECTED`) + evidencia conservada; supersession como
  candidato de relación para revisión, nunca aplicada.
- **Reachability observacional:** `expected` en perfil vs `observed` en
  ejecución; divergencia = drift registrado.
- **Version candidates no publicables:** enum existente conservado;
  `RESOLVED` redefinido como resolución documental mecánica.
- **Fail-closed:** cada eslabón ausente produce estado explícito
  (`UNPROBED`, `UNREACHABLE`, `REQUIRES_MANUAL_REVIEW`,
  `REBASELINE_REQUIRED`) — nunca silencio, nunca `PERMITTED`.

## F. Riesgos y preguntas abiertas

1. **~11 superficies sin sondear** — la hipótesis de familias puede romperse;
   -A existe precisamente para medirlo antes de comprometer implementación.
2. **Canonicalizers por familia** — riesgo de normalización excesiva; mitigado
   por la regla "solo ruido demostrado" + `REBASELINE_REQUIRED`.
3. **Infra `es_local`** — el runner programado es decisión operativa;
   el diseño no la bloquea (agnóstico por `runner_network`).
4. **Licencias por fuente** — el atlas registra términos por fuente y
   artefacto; `DIGEST_ONLY` por defecto donde no estén verificados.
5. **Ceuta/Melilla** — boletines provinciales/ciudad con estructura propia;
   pueden quedar `UNPROBED(reason)` si no hay superficie máquina verificable —
   eso es un resultado válido del atlas, no un fracaso.
6. **`boe_xml` por bloques** — formato nuevo; coste acotado a una familia,
   solo en -C.

## H. Self-review de la spec

- ¿Toda afirmación arquitectónica citada? Sí: cada decisión remite a G0,
  M10.1 (matriz de pilotos, código real en `97a60ee`) o al gate OSS de la
  segunda pasada; las hipótesis no probadas (clustering de familias) están
  marcadas como tales y son precisamente lo que -A mide.
- ¿Se cuela implementación? No: los shapes de §C son contratos de datos, no
  código; ningún archivo de `pipeline/` se propone modificar todavía.
- ¿Reduce garantías? No: las cuatro precisiones del owner están incorporadas
  verbatim (20 dominios ≠ 20 fuentes; runner agnóstico con `es_local` como
  deployment inicial; canonicalizer versionado + `REBASELINE_REQUIRED`;
  `DISAPPEARED_SUSPECTED` por perfil; `RESOLVED` = documental-mecánico).
- ¿Reproducible? La evidencia base está mergeada; los probes nuevos usarán el
  mismo verificador con transport inyectado y live gate de ejecución.
- ¿Límite legal? Reforzado: se fija explícitamente que `RESOLVED` y los
  version candidates no son publicables y que refresh jamás muta reglas.
