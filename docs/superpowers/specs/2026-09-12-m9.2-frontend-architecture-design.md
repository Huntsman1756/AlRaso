## 0. Decisión resumida

Se recomienda el enfoque **A: NATIVE ES MODULES, sin bundler y sin build step de producto**:

- `index.html` carga `<script type="module" src="/app.js">`; `app.js` se reduce a composition/bootstrap.
- Doce módulos cohesivos en `webapp/static/modules/*.js` con imports/exports explícitos, sin side effects al importar.
- `store.js` permanece como script clásico untouched (compatibility boundary, opción A del contrato M9.2; conserva su camino de test Node vía `module.exports`).
- `sw.js` se modifica exclusivamente para añadir los nuevos módulos a `SHELL_URLS` y bump de versión de `SHELL_CACHE` (v1 → v2). `/api/*` sigue NETWORK_ONLY; Open-Meteo sigue pass-through.
- `webapp/server.py` recibe UNA extensión data-only aprobada por el owner: nuevas entradas en el dict `STATIC_FILES` para servir los módulos. Ninguna línea legal/resolver/routing se toca. El diff completo queda acotado en la sección L.
- Cero cambios visuales: `style.css` con diff cero, mismos hooks DOM, mismo orden de listeners, mismo comportamiento de sheet, mismo hotfix de resultado stale (S03/S04/S14 intactos).

El objetivo no es "app.js tiene X líneas": es que "cambiar weather no exige entender el resolver visual" y que cada responsabilidad tenga ownership identificable.

### A.2 Modelo de carga y serving actual

## D. Enfoques posibles

| | A. Native ES Modules | B. Classic script split / IIFE namespace | C. Framework/bundler (React/Vue/Svelte/Vite) |
|---|---|---|---|
| Qué cambia | `<script type="module">` + módulos con imports/exports explícitos | varios `<script src>` clásicos + namespaces globales | migración completa de UI |
| Dependencias explícitas | SÍ: el grafo ES es el contrato; ciclos imposibles sin romper el runtime | NO: dependencias implícitas por orden de carga y globals compartidos | parcial (su propio sistema) |
| Fronteras de confianza visibles | SÍ: `api-legal.js` vs `api-cartography.js` vs Open-Meteo en módulos distintos | difuminadas en namespace | abstracta propia del framework las oculta |
| PWA/offline | SHELL_URLS + SWR existentes; SW sigue igual semánticamente | igual, pero cada script es un global más | requiere build/bundle precacheado |
| Riesgo sobre hotfix P0 | bajo: el guard se traslada entero con sus tests | medio (mismo movimiento, más colisión de globals) | alto (reescritura = nueva superficie de bugs legales) |
| Coste servidor | +12 entradas data-only en whitelist (aprobadas) | +12 igualmente | build de producto PROHIBIDO por el hito |
| Side effects al cargar | ninguno (policy + test de import en Node) | IIFEs ejecutan al cargar (como hoy, pero multiplicado) | runtime entero |
| Veredicto | **RECOMENDADO** | REJECT: no aporta dependencias explícitas y mantiene el problema de globals/orden | REJECT: sin ventaja proporcional; el hito lo prohíbe |

Conclusión: A cumple el objetivo arquitectónico con el menor cambio de plataforma. B no resuelve el problema (globals implícitos). C se evalúa y se rechaza: la ventaja esperada (UI reactiva) no es el problema de AlRaso; el problema es ownership y dependencias explícitas.

## H. Policy de side effects y ownership

- NINGÚN módulo ejecuta DOM/fetch/listeners/timers al importarse. Todo efecto vive en `createX(...).init()`/`boot()` invocado desde `app.js` en el orden de la sección I. El test de loadability (Node importa cada módulo con un `document`/`window` ausentes) falla si se rompe.
- Acceso permitido por módulo: ver columna SIDE EFFECTS de G. Cualquier ampliación = cambio de spec.
- `localStorage`: SOLO via AlRasoStore (inyectado). Nada nuevo.
- `location.hash`: SOLO app.js (navegación). Timers: SOLO connectivity (interval 30 s) y probe abort (4 s), y el `setTimeout` de resize del mapa (map.js/sheet.js como hoy).
- innerHTML: se traslada tal cual (mismos puntos, mismas sanitizaciones con `esc`); prohibido introducir innerHTML nuevo con datos de API/OSM; preferir textContent al mover si y solo si no cambia el resultado renderizado.

## I. Boot sequence BEFORE / AFTER
