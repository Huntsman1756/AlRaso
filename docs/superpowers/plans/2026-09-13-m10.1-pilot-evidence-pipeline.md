# AlRaso M10.1 — Pilot Evidence Pipeline (plan de implementación)

**Estado:** plan para aprobación antes de implementar.
**Spec aprobada:** `docs/superpowers/specs/2026-09-13-m10-spain-coverage-scaling-design.md` (mergeada en `50d9910`, §P registra aprobación con 3 correcciones de contrato aplicadas).
**Base:** `origin/main` = `50d9910`.
**Rama de trabajo prevista:** `feat/m10.1-pilot-evidence-pipeline` en worktree aislado.

Este documento convierte la spec M10 en unidades pequeñas y reversibles. La
creación del plan no implementa nada. Ninguna tarea se ejecuta hasta que el
owner apruebe explícitamente este plan.

## 0. Decisiones bloqueadas (de la spec, no se reabren)

```text
DISCOVERY != FETCH != PARSE != VERSION_RESOLUTION
GEOMETRY_DISCOVERY != LEGAL_SCOPE
AUTOMATED_EXTRACTION != PUBLICATION
SOURCE_UNREACHABLE != SOURCE_ABSENT

MONOLITHIC_SOURCE_ADAPTER = REJECTED
LEGAL_ENGINE (alraso/) = FROZEN — diff cero esperado
WEBAPP = FROZEN — diff cero esperado
NEW_RULE_PUBLICATION = FORBIDDEN en M10.1
PERMITTED nunca inferido por ausencia de cobertura

VALID = effective_from/to | SYSTEM = recorded_at/until | publication_date
NO existe tercer par temporal (knowledge_from/to eliminados)

scope_evidence_status ∈ {CONTEXT_ONLY, OFFICIAL_SCOPE_CANDIDATE,
                         OFFICIAL_SCOPE_LINK_PROVEN}; default CONTEXT_ONLY;
solo evidencia revisada alcanza OFFICIAL_SCOPE_LINK_PROVEN

reachability = expectativa en perfil (expected + fallback);
verdad de ejecución = runner_network / reachability_observed /
observed_at / evidence_sha256
```

Objetivo exacto de M10.1: **la misma pipeline prepara 5 `ReviewPacket`
reproducibles (P1–P5) sin lógica específica de parque o CCAA en el motor
legal. Cero reglas publicadas.**

## 1. Reglas de ejecución

Cada tarea sigue el gate atómico de M9.2:

```text
test RED (contrato) → implementación mínima → test GREEN →
regresión relevante → commit → siguiente
```

Reglas adicionales específicas de pipeline:

- **Los tests NUNCA tocan red.** Los fetchers se prueban contra los bytes de
  evidencia G0 ya commiteados (`discovery/evidence/spain-coverage-g0/`) —
  son fixtures grabados con provenance real. El acceso en vivo es solo para
  el verificador (`tooling/m10_*_verify.py`), que corre manual/como job
  separado y reporta `reachability_observed`.
- **Nada de lógica jurisdiccional en providers compartidos**: si una tarea
  necesita `if jurisdiction == ...`, se detiene y se documenta — la
  peculiaridad va al `SourceProfile` o a un recipe nuevo.
- **Soft-404 siempre validado**: todo fetch exige `content_marker` del perfil;
  HTTP 200 sin marcador = `FAIL`, nunca éxito silencioso.
- **Geometría/PDF oficial**: `DIGEST_ONLY`/`METADATA_ONLY` por defecto; la
  evidencia almacena digest + URL re-fetcheada, salvo reuse verificado.
- Una tarea que descubra que la spec miente en algo: STOP, documentar,
  actualizar spec — no improvisar.

Dependencias: **stdlib only** si es posible (yaml → JSON con schema si PyYAML

### Tasks 11–14 — Pilotos P2–P5 (una tarea por jurisdicción)

Cada una = perfil nuevo + provider/recipe nuevo solo si el formato lo exige:

- **P2 BOA** (`boa.profile.yaml`): `boa_cgi` discovery (DOCN), fetcher GET,
  parser `pdf_text`/`html_marker`. Fixture: `boa-decreto-16-2022-doc.html`.
- **P3 BOC Cantabria** (`boc-cantabria.profile.yaml`): recipe
  `POST→TOC→verXmlAction` — la prueba de fuego del diseño: discovery y fetch
  se ejercitan por separado, `reachability.expected.foreign_ci=ES_ONLY_SUSPECTED`,
  fallback `es_local_fetcher`. Fixtures: `boc-cantabria-*.xml/html`.
- **P4 DOGC** (`dogc.profile.yaml`): `dogc_socrata` discovery + ELI→AKN fetch;
  parser `akn` mínimo (extraer `eId`/artículos; patrón de `akn-profiler`,
  sin dependencia obligatoria). Fixture: `dogc-39-2003-akn.xml`.
- **P5 BOC Canarias** (`boc-canarias.profile.yaml`): discovery por ID
  `BOC-A-*`, fetch HTML+PDF firmado, parser `pdf_text` (extract G0 como
  marcador). Fixture: `boc-canarias-182-2025.html` + `boc-182-2025-vivac-extract.txt`.

Gate por piloto: mismo código de `pipeline/`, solo difieren `sources/*.profile.yaml`
+ fixtures + (si hace falta) un provider/recipe nuevo. Si un piloto exige
tocar `alraso/` o `webapp/` → STOP, diseño erróneo.

## 5. Fuera de scope explícito

- `VersionResolver.consolidated_api` completo (BOE/DOGC): M10.2+.
- Fetcher ES-local real (infra): M10.1 solo declara `fallback` en perfil y
  registra `UNREACHABLE` honesto; la infra se decide con evidencia de P3.
- Inventario nacional completo (17 CCAA / ENP total): post-M10.1.
- Automatización de apertura de PRs (foul-flock pattern completo): M10.2+;
  M10.1 genera el `ReviewPacket` como artefacto, la PR la abre un humano.

## 6. Riesgos conocidos (de §M de la spec)

- PyYAML puede no estar en stdlib — perfiles en JSON si hace falta (decisión
  Task 2, documentada).
- `pdftotext` externo: parser declara `available=False` limpio.
- MITECO ALTCHA no se toca en M10.1 (inventario semilla = evidencia G0).
- BOC Cantabria en CI extranjero → `INCONCLUSIVE` esperado del verificador,
  no fallo del piloto (el replay offline sí exige PASS).
